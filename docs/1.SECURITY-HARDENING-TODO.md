# P0 — live credential exposure

## [ ] P0-1. Rotate everything that was in `.env.prod`

`.env.prod` was committed in **`1195455e`** and removed in `da0cb264`.
`1195455e` is an ancestor of `main` in a **public** repo, so its contents are
readable right now at
`github.com/aitechnologysys-sys/veroza/commit/1195455e`.

Inspect it (do **not** paste values into a chat or ticket):

```bash
git show 1195455e:.env.prod
```

~47 keys. Rotate in this order:

1. **`JWT_SECRET`** — forges a session for any account. Rotating logs everyone
   out; that is the point.
2. **`DATABASE_URL` password**, **`RESEND_API_KEY`**, **`EMAIL_PASS`** — data
   access and outbound-email abuse from your domain.
3. **`POLAR_ACCESS_TOKEN`**, **`POLAR_WEBHOOK_SECRET`**, and any `STRIPE_*` —
   billing.
4. **`CLOUDFLARE_*`**, **`NGROK_AUTHTOKEN`**, **`OPENAI_API_KEY`** — cost abuse.
5. All social `*_CLIENT_SECRET` / `X_API_SECRET` — regenerate in each developer
   console.

**Do not** try to fix this by rewriting history. The commit has been public,
GitHub caches commit objects independently of branches, and any clone or fork
keeps it. Rotation is the only reliable remediation.

**How to apply a rotation:** edit `.env.prod` on the VM, then
`docker compose -p postaryx up -d postaryx`. No rebuild, no re-pull — config is read
at container start. Seconds.

## [x] P0-2. Get database passwords out of the committed compose file — done

Both `docker-compose.yaml` (prod) and `docker-compose.dev.yaml` (dev) now source
Postgres user/password/db from `${...}` substitution instead of hardcoded
literals, with `:?` so Compose refuses to start rather than silently falling
back to a weak default:

```yaml
# docker-compose.yaml (prod) — postaryx-postgres service
environment:
  POSTGRES_PASSWORD: ${POSTARYX_DB_PASSWORD:?set POSTARYX_DB_PASSWORD in .env}
  POSTGRES_USER: ${POSTARYX_DB_USER:?set POSTARYX_DB_USER in .env}
  POSTGRES_DB: ${POSTARYX_DB_NAME:-postaryx-db-prod}
```

```yaml
# docker-compose.dev.yaml — postaryx-postgres service
environment:
  POSTGRES_PASSWORD: ${POSTARYX_DEV_DB_PASSWORD:?set POSTARYX_DEV_DB_PASSWORD in .env}
  POSTGRES_USER: ${POSTARYX_DEV_DB_USER:?set POSTARYX_DEV_DB_USER in .env}
  POSTGRES_DB: ${POSTARYX_DEV_DB_NAME:-postaryx-db-local}
```

**Named `POSTARYX_DB_*` / `POSTARYX_DEV_DB_*`, not generic `POSTGRES_*`,
deliberately.** Compose reads `${...}` substitutions from whatever `.env` sits
next to the compose file being run — for both files locally, that's the
repo-root `.env`, which already defines a dev `DATABASE_URL`. Generic names
risked collision; the prefixed pair keeps dev and prod distinct in the same
file. `DATABASE_URL` in the `postaryx` service is built from the same
`POSTARYX_DB_*` vars (not a separate hardcoded string), so it can't drift from
what the Postgres container is actually initialized with. The repo-root `.env`
now holds both var sets — `POSTARYX_DEV_DB_*` also feeds `DATABASE_URL` for
`pnpm dev` via `dotenv-expand`, so dev's credential is defined exactly once.

🔴 **Critical ordering detail** (didn't apply here, but matters for a live
box): `POSTGRES_PASSWORD` only takes effect when the data directory is **first
initialised**. On an existing volume, changing it does nothing — you must
either:

```bash
docker exec -it postaryx-postgres psql -U postaryx-user -d postaryx-db-prod \
  -c "ALTER USER \"postaryx-user\" WITH PASSWORD 'new-strong-password';"
```

…or destroy the volume and start fresh (`docker compose -p postaryx down -v`,
which **deletes all data**). Verified clean here: no prod-stack Postgres volume
had ever been initialized yet, so this rotation took effect immediately with
no migration step.

**Still to do on first real deploy:** the VM's own `.env` (next to
`docker-compose.yaml`, alongside `POSTARYX_PUBLIC_URL` — see
`ORACLE-VM-DEPLOYMENT.md` §7) needs `POSTARYX_DB_USER` / `POSTARYX_DB_PASSWORD`
/ `POSTARYX_DB_NAME` added before first `up`, or Compose will refuse to start.

# P1 — network exposure

## [x] P1-1. Bind the dev stack's ports to loopback — done

All six of `docker-compose.dev.yaml`'s published ports (`postaryx-postgres`
`5432`, `postaryx-redis` `6379`, `postaryx-pg-admin` `8082`,
`postaryx-redisinsight` `5540`, `temporal` `7233`, `temporal-ui` `8080`) are
now `127.0.0.1:<port>:<port>` instead of the bare `<port>:<port>` form, which
Docker publishes on `0.0.0.0` (every interface, including whatever Wi-Fi
you're on).

Verify:

```bash
node -e '
const y=require("yaml"),fs=require("fs");
const d=y.parse(fs.readFileSync("docker-compose.dev.yaml","utf8"));
for(const [n,s] of Object.entries(d.services||{}))
  for(const p of (s.ports||[]))
    console.log((String(p).startsWith("127.0.0.1")?"OK  ":"OPEN")+"  "+n+"  "+p);'
```

Verified: all six lines read `OK`. Also confirmed live — brought up
`postaryx-postgres`/`postaryx-redis` and checked `docker inspect
.NetworkSettings.Ports`, both show `HostIp: 127.0.0.1` only.

## [x] P1-2. Loopback-publish Postgres in production, for DBeaver — done

This is the production answer to "how do I connect DBeaver," done the same way
`temporal-ui` already was:

```yaml
# docker-compose.yaml — postaryx-postgres service
ports:
  # Loopback-ONLY. The leading 127.0.0.1 is the entire security control: it
  # binds to the VM's internal interface, unreachable from outside. Reach it
  # through an SSH tunnel — same approach as temporal-ui:8080.
  - '127.0.0.1:5432:5432'
```

🔴 **Never remove the `127.0.0.1:` prefix, or write a bare `"5432:5432"`.**
Docker writes its own iptables rules and **bypasses `ufw`**, so that publishes
your database straight to the internet — guarded by a password that is in a
public repo history (P0-1). This is the single most dangerous change you could
make to this stack.

Verified locally: `docker inspect postaryx-postgres` shows `HostIp: 127.0.0.1`
only, and a direct `psql -h 127.0.0.1 -p 5432` connection from the host works
with no bridge container needed (superseding the old socat-bridge workaround
at the top of this doc).

On the VM, reach it from your Mac by tunneling — either manually:

```bash
ssh -i your-key.key -L 5434:127.0.0.1:5432 ubuntu@<VM_PUBLIC_IP>
# leave that running, then point DBeaver at 127.0.0.1:5434
```

…or let DBeaver do it (nicer — it reconnects for you):

**DBeaver → connection → SSH tab**

| Field | Value |
|---|---|
| Use SSH Tunnel | ✅ |
| Host / Port | `<VM_PUBLIC_IP>` / `22` |
| User Name | `ubuntu` |
| Authentication | Public Key → your `.key` file |

**Main tab**

| Field | Value |
|---|---|
| Host | `127.0.0.1` ← resolved *on the VM*, after the tunnel |
| Port | `5432` |
| Database | `POSTARYX_DB_NAME` from `.env` |
| Username | `POSTARYX_DB_USER` from `.env` |
| Password | `POSTARYX_DB_PASSWORD` from `.env` — the rotated one from P0-2 |

Verify from your Mac that the port is **not** open publicly:

```bash
nc -z -w5 <VM_PUBLIC_IP> 5432 && echo "EXPOSED — fix immediately" || echo "OK: not reachable"
```

Two habits for production access:

- Do P0-2 **before** enabling this. Don't tunnel to a database whose password is
  on GitHub.
- In DBeaver set the **connection type to Production** — it colours the UI red
  and prompts before writes.

## [x] P1-3. Give Redis a password and a memory cap — done (prod only)

`docker-compose.yaml`'s `postaryx-redis` now requires auth and caps memory,
sourced from `.env` (`POSTARYX_REDIS_PASSWORD`, matching the `POSTARYX_DB_*`
naming from P0-2):

```yaml
postaryx-redis:
  command:
    - redis-server
    - --requirepass
    - ${POSTARYX_REDIS_PASSWORD:?set POSTARYX_REDIS_PASSWORD in .env}
    - --maxmemory
    - 256mb
    - --maxmemory-policy
    - allkeys-lru
```

`REDIS_URL` in the `postaryx` service and the healthcheck (`redis-cli -a
${POSTARYX_REDIS_PASSWORD} --no-auth-warning ping`) both read the same var.
Verified: unauthenticated `redis-cli ping` gets `NOAUTH Authentication
required`, authenticated ping/config confirm `maxmemory=268435456` (256 MB) and
`maxmemory-policy=allkeys-lru`, and the Compose healthcheck reports `healthy`.

**Scoped to prod only.** Dev's `postaryx-redis` (`docker-compose.dev.yaml`) is
left password-free on purpose — it's throwaway local cache data, and adding
auth there costs zero-friction debugging (RedisInsight, ad-hoc `redis-cli`)
for no real security benefit given P1-1 (loopback binding) is the actual open
risk on the dev stack, not Redis auth.

Watch actual usage before trusting 256 MB:

```bash
docker exec postaryx-redis redis-cli -a "$POSTARYX_REDIS_PASSWORD" --no-auth-warning info memory | grep used_memory_human
```

# P2 — application configuration

## [ ] P2-1. Close public registration

```yaml
DISABLE_REGISTRATION: 'false'   # docker-compose.yaml line 64
```

Anyone who finds the URL can create an account. Fine while nobody knows the
domain; not fine once it's public and you're paying for AI calls per user. Set to
`'true'` as soon as your own accounts exist.

## [ ] P2-2. Keep `NOT_SECURED` unset in production — verify, don't assume

Currently correct: not present in `docker-compose.yaml`, and commented out in
`.env.example`. Worth knowing what it does, because setting it would be severe —
it drops `credentials: true` from CORS **and** exposes `auth`, `showorg` and
**`impersonate`** headers (`apps/backend/src/main.ts:26-43`).

```bash
docker exec postaryx printenv NOT_SECURED || echo "OK: unset"
```

CORS itself is fine — restricted to `FRONTEND_URL` and `MAIN_URL`, no wildcard.
Auth cookies are `secure: true, httpOnly: true, sameSite: 'none'`. No action.

## [ ] P2-3. Add security headers at the host nginx

The container's nginx sets `X-Content-Type-Options` and a CSP, but **only on the
`/uploads/` block**. The app itself gets none.

The host nginx terminates TLS, so that's the right place for HSTS. Add to the
vhost from `ORACLE-VM-DEPLOYMENT.md` §7, *after* Certbot works:

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
server_tokens off;
```

Don't add HSTS before HTTPS works — you'll lock yourself out of the plain-HTTP
version while debugging.
