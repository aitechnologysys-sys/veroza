# Multi-Domain Deployment Walkthrough — landing + app + api on `postaryx.com`

**Purpose.** Stand up the full public surface — marketing site, product app, and
API — on `postaryx.com`, end to end, with HTTPS.

**Status: live.** The apex and `www` were cut over on 2026-08-25 and verified
(§9). `app.postaryx.com` is the remaining piece. An earlier rehearsal on
`agentengine.studio` is being decommissioned — §10.

**DNS lives at Cloudflare** (the domain is registered with Cloudflare Registrar,
so the zone is on Cloudflare's nameservers by default). That shapes §4 in ways a
generic Vercel guide will not tell you.

**Companion docs.** This one covers *domains and routing*. It assumes the VM
already exists and the stack already runs on `127.0.0.1:4007` — that is
[2. ORACLE-CLOUD-SETUP-WALKTHROUGH.md](./2.%20ORACLE-CLOUD-SETUP-WALKTHROUGH.md)
§1–7. It replaces that doc's §8 (which only covered a single apex host serving

## 1. The topology, and why it's the right one

| Hostname | Serves | Runs on | Indexable |
|---|---|---|---|
| `postaryx.com` | Marketing site + `/docs` | Vercel (`clientside-landing`) | **Yes** — this is the SEO surface |
| `www.postaryx.com` | 308 → apex | Vercel | No |
| `app.postaryx.com` | Postaryx frontend | Oracle VM (Docker Compose) | No — `noindex` |
| `app.postaryx.com/api` | Postaryx backend (NestJS) | Oracle VM, **same container** | No |

**`/api` is not a decision you have to implement — it's already how the image
works.** `var/docker/nginx.conf` inside the container listens on `:5000` and
routes:

```
/api/     → http://localhost:3000/   (NestJS backend)
/uploads/ → /uploads/                (local disk, served directly)
/         → http://localhost:4200/   (Next.js frontend)
```

So one host vhost proxying `app.postaryx.com` → `127.0.0.1:4007` gives you the
frontend *and* the API at `/api`, from one cert, one origin, with no CORS.
`docker-compose.yaml` already encodes exactly this assumption:

```yaml
MAIN_URL:                 ${POSTARYX_PUBLIC_URL}
FRONTEND_URL:             ${POSTARYX_PUBLIC_URL}
NEXT_PUBLIC_BACKEND_URL:  ${POSTARYX_PUBLIC_URL}/api   # ← the /api is appended for you
BACKEND_INTERNAL_URL:     http://localhost:3000
```

Set `POSTARYX_PUBLIC_URL=https://app.postaryx.com` and every one of those is
right.

**Why not `api.postaryx.com`.** It would cost you a second vhost, a second cert,
a CORS allowlist, `sameSite`/cookie-domain care on every auth response — and buy
nothing, because `BACKEND_INTERNAL_URL` stays `http://localhost:3000` regardless
(the frontend's server-side calls never leave the container). Same-origin `/api`
is what upstream Postiz assumes; diverging here means re-fixing it on every
`git merge upstream/main`.

**Why the apex is marketing, not the app.** Search engines treat subdomains as
largely separate properties for authority. The apex is the strongest asset and
the thing people type. Putting a login screen there spends it on nothing while
pricing, features, and the `/docs` tree accrue authority elsewhere.

**Why the landing goes to Vercel and the app does not.** The landing is a plain
Next.js app with no stateful dependencies except a Neon Postgres for the
waitlist — it is a natural fit, it's free, and it keeps marketing deploys
independent of product deploys. The *app's* frontend cannot move to Vercel:
its auth cookie's `Domain` is derived from `FRONTEND_URL`, three pages call
`BACKEND_INTERNAL_URL` on localhost, and all three Node processes build and run
as one unit behind the internal nginx. Full reasoning in
[4. CONTAINMENT-DEPLOYMENT-PLAN.md](./4.%20CONTAINMENT-DEPLOYMENT-PLAN.md) §1.

If you'd rather not use Vercel at all, §11 has the single-VM alternative.

## 2. Prerequisites — confirm these before touching DNS

- [ ] `postaryx.com` is registered and you control its DNS (Cloudflare).
- [ ] Oracle VM exists, running, and you know `<VM_PUBLIC_IP>`.
- [ ] Steps §1–7 of
      [2. ORACLE-CLOUD-SETUP-WALKTHROUGH.md](./2.%20ORACLE-CLOUD-SETUP-WALKTHROUGH.md)
      are done: Docker installed, `.env` + `.env.prod` written, stack up.
- [ ] `docker compose -p postaryx ps` — every container `healthy`/`running`.
- [ ] `curl -I http://127.0.0.1:4007` on the VM → `200`.
- [ ] `curl -I http://127.0.0.1:4007/api/` on the VM → any HTTP response, **not**
      `502`/`Connection refused`. A `502` here means the backend died at
      Temporal connect time; fix that before doing anything with domains (see
      the long comment on the `temporal` service in `docker-compose.yaml`).
- [ ] OCI Security List has ingress on TCP **80** and **443** from `0.0.0.0/0`,
      and SSH (22) from your IP. Both layers — Security List *and* `ufw` — must
      allow it; see §5–6 of the Oracle walkthrough, and §5 below.

Order matters and it is not negotiable: **DNS → TLS → app config.** Let's
Encrypt validates over plain HTTP on port 80, so no cert can be issued before
`app.postaryx.com` resolves to the VM and 80 is reachable from the internet.

## 4. DNS at Cloudflare

Add the apex and `www` to the Vercel project **first** (§7.3) — Vercel prints the
exact record values on that screen, and they are per-project. Copy them from
there. Do not paste values from memory or from a blog post.

### 4.1 The records

| Type | Name | Content | Proxy status | TTL |
|---|---|---|---|---|
| CNAME | `@` | the target Vercel shows (`<hash>.vercel-dns-0NN.com`) | **DNS only** | Auto |
| CNAME | `www` | the target Vercel shows | **DNS only** | Auto |
| A | `app` | `<VM_PUBLIC_IP>` | **DNS only** | Auto |
| TXT | `_vercel` | only if Vercel asks for it (domain verification) | n/a | Auto |

### 4.2 A CNAME on the apex is fine here

Vercel now issues per-project DNS targets and often shows **only a CNAME**, with
no A record, even for the apex. A CNAME at the zone apex is normally illegal DNS
— but Cloudflare performs **CNAME flattening**: it resolves the target itself and
answers with the resulting A records. Cloudflare displays a notice saying exactly
this. It is informational, not a warning.

Flattening works whether or not the record is proxied. The flattening is what
makes the apex CNAME legal; the proxy toggle is a separate, unrelated setting.

Verified live: `dig +short postaryx.com` returns Vercel's addresses
(`216.198.79.1`, `64.29.17.1` as of 2026-08-25) rather than a CNAME, which is
flattening working as intended.

### 4.3 Every record must be grey-cloud (DNS only)

Cloudflare defaults new records to **Proxied (orange cloud)**. Click the cloud on
each of the three records to turn it grey. Both reasons point the same way:

- **Orange on the Vercel records** — Vercel cannot complete its certificate
  challenge, and requests can land in a redirect loop (`ERR_TOO_MANY_REDIRECTS`)
  unless Cloudflare's SSL mode is Full (strict).
- **Orange on `app`** — Certbot's HTTP-01 challenge never reaches your VM, so no
  certificate is issued. `dig` gives this away immediately: you get Cloudflare
  anycast addresses (`104.21.x.x`, `172.67.x.x`) instead of `<VM_PUBLIC_IP>`.

You can put Cloudflare's proxy in front of `app.` later if you want its WAF and
caching, but only after the cert exists and only with SSL mode **Full (strict)**
— never Flexible. It complicates renewals and WebSocket upgrades. Default answer:
leave it grey.

### 4.4 Clear out registrar leftovers

Cloudflare Registrar can leave placeholder records on a freshly registered
domain. Before adding anything, delete from the DNS → Records list:

- any pre-existing `A @` / `AAAA @` / `CNAME www` — a conflicting apex record is
  the most common cause of "Invalid Configuration" in Vercel;
- any **wildcard `*` record** — it silently answers for every subdomain you have
  not explicitly defined, including `app`, which produces a confusing
  "why is Cloudflare answering for a host I never created" symptom.

Leave `MX` and any mail-related `TXT` records alone if you have email on the
domain.

### 4.5 Verify before continuing

```bash
dig +short postaryx.com        # Vercel's addresses
dig +short www.postaryx.com    # Vercel's CNAME target, then its addresses
dig +short app.postaryx.com    # exactly <VM_PUBLIC_IP>, one address, nothing else
```

If `app` returns two addresses in `104.21.*` / `172.67.*`, it is still proxied or
a wildcard is catching it. Fix that before touching Certbot.

Propagation is not instant. If `dig` returns a stale answer, check the record's
TTL before assuming a mistake.

## 5. The app subdomain on the VM: vhost, firewall, TLS

SSH in: `ssh -i ~/.ssh/postaryx-oci.key ubuntu@<VM_PUBLIC_IP>`

### 5.1 Install nginx and add the WebSocket upgrade map

Install first — `/etc/nginx/` does not exist until you do, and the `tee` below
fails with `No such file or directory` if you run it out of order:

```bash
sudo apt install -y nginx
```

The vhost needs `map $http_upgrade $connection_upgrade` in the `http` block.
Hardcoding `proxy_set_header Connection "upgrade"` sends an upgrade header on
*every* request including plain page loads, which some proxies and HTTP/2 paths
reject. Ubuntu's `nginx.conf` includes `/etc/nginx/conf.d/*.conf` inside `http`,
so a drop-in file is the right home for it:

```bash
sudo tee /etc/nginx/conf.d/upgrade-map.conf > /dev/null <<'EOF'
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
EOF
```

Confirm the include is really there before relying on it — a `map` in a file
nginx never reads produces `unknown variable "connection_upgrade"` at
`nginx -t` time:

```bash
grep -n include /etc/nginx/nginx.conf   # expect conf.d/*.conf AND sites-enabled/*
```

### 5.2 The vhost

Write it with `tee` rather than editing by hand — it is idempotent, and if you
ever need to reset the file (see §5.6) this is the exact block to reset it to:

```bash
sudo tee /etc/nginx/sites-available/postaryx-app.conf > /dev/null <<'EOF'
server {
    listen 80;
    listen [::]:80;
    server_name app.postaryx.com;

    # Postaryx accepts uploads up to 2G (matches the container's internal nginx).
    client_max_body_size 2G;

    # The app must never compete with the marketing site in search results.
    # Set at the server level so it applies to /api and /uploads too.
    add_header X-Robots-Tag "noindex, nofollow" always;

    location / {
        # 4007 is the loopback-only publish of the container's :5000. That one
        # upstream serves the frontend, /api, and /uploads — see §1.
        proxy_pass http://127.0.0.1:4007;
        proxy_http_version 1.1;

        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade           $http_upgrade;
        proxy_set_header Connection        $connection_upgrade;

        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }
}
EOF
```

**The quotes around `'EOF'` are load-bearing.** With a bare `<<EOF`, the shell
expands `$host`, `$scheme`, `$http_upgrade` and friends *before* the text reaches
the file — they are all unset, so each becomes an empty string and you get
`nginx: [emerg] invalid number of arguments in "proxy_set_header" directive`.
Quoting the delimiter makes the heredoc literal. Same applies to the `map` block
in §5.1.

There is **no second `location /api`** block, and adding one would be a mistake:
`location /` already forwards `/api/*` to `127.0.0.1:4007`, and the container's
internal nginx does the split. A host-level `/api` block would strip or rewrite
the prefix and break every request.

Enable it and reload:

```bash
sudo ln -s /etc/nginx/sites-available/postaryx-app.conf /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx
```

`sites-enabled/` must contain a **symlink**, not a copy. If it holds a real file,
you will edit `sites-available/` and nginx will keep serving the stale copy —
`nginx -T` then shows config you are sure you changed. `ls -l
/etc/nginx/sites-enabled/` tells you which you have.

### 5.3 Open the host firewall

The OCI Security List (§2) is the cloud layer; `ufw` is the host layer. Traffic
must pass **both**, and a request blocked by either looks identical from outside
— `curl` just hangs.

```bash
sudo ufw allow 'Nginx Full'
sudo ufw status verbose
```

Prove it from your Mac, not from the VM — from the box itself everything always
looks fine:

```bash
curl -sI http://app.postaryx.com | head -1    # expect 200
```

A `404` here with `Server: nginx/…​ (Ubuntu)` means the request reached the VM but
your vhost is not the block handling it — see §5.6.

If it hangs: `sudo iptables -L INPUT -n --line-numbers` on the VM. Oracle's
stock images ship a catch-all `REJECT` near the end of the INPUT chain, and
`ufw` rules can land *below* it. Insert above it and persist:

```bash
sudo iptables -I INPUT 6 -p tcp --dport 80  -j ACCEPT
sudo iptables -I INPUT 7 -p tcp --dport 443 -j ACCEPT
sudo netfilter-persistent save     # without this the rules die on reboot
```

The `6`/`7` are typical, not guaranteed — read the line numbers first.

### 5.4 Certificate

```bash
sudo snap install core; sudo snap refresh core
sudo snap install --classic certbot
sudo ln -sf /snap/bin/certbot /usr/bin/certbot

# -m is the ACME account contact: expiry warnings and renewal-failure notices
# go here. Use an address you actually monitor, on a domain you control.
sudo certbot --nginx -d app.postaryx.com --redirect --agree-tos -m <your-email>

sudo systemctl status snap.certbot.renew.timer   # auto-renewal is scheduled
sudo certbot renew --dry-run                     # renewal actually works
```

Only `app.` goes on this cert. The apex and `www` are Vercel's — Vercel issues
and renews those itself.

Certbot edits the vhost in place: it converts your existing block to
`listen 443 ssl` and appends a small new `:80` block that 301s to HTTPS. Your
`add_header X-Robots-Tag` and `client_max_body_size` therefore stay on the block
that now serves HTTPS — but confirm rather than assume, since `add_header` in
nginx does not inherit into a block that declares its own:

```bash
grep -n "listen\|X-Robots-Tag\|client_max_body_size" /etc/nginx/sites-available/postaryx-app.conf
```

### 5.5 Security headers — after HTTPS works, not before

In the `:443` server block Certbot created:

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
server_tokens off;
```

```bash
sudo nginx -t && sudo systemctl reload nginx
```

Note `includeSubDomains` on `app.postaryx.com` only affects hosts *under* `app.`,
so it cannot affect the apex. HSTS before HTTPS works would lock your own browser
out of the plain-HTTP fallback while you're still debugging — that's why this is
last.

### 5.6 When the vhost fights you

Three failures account for nearly all of it.

**`404 Not Found` from `nginx/…​ (Ubuntu)`.** The request reached the VM but was
answered by a different server block — usually the stock `default` site, which is
`default_server` and wins when your vhost is not enabled. Check
`ls -l /etc/nginx/sites-enabled/`, then re-run the enable step in §5.2.

**`invalid number of arguments in "proxy_set_header"`.** An nginx variable in
the file is empty. Almost always a heredoc written with `<<EOF` instead of
`<<'EOF'` (§5.2), which let the shell eat every `$…` on the way in. Confirm with
`grep -n proxy_set_header /etc/nginx/sites-available/postaryx-app.conf` — a line
reading `proxy_set_header Host ;` is the tell — then rewrite the file with the
delimiter quoted.

**`nginx -T` shows config you are certain you changed.** `nginx -T` re-reads the
files from disk, so it is telling the truth: the file nginx loads is not the file
you edited. Find the real one:

```bash
sudo nginx -T 2>/dev/null | grep -B5 "server_name" | grep "configuration file"
```

Two causes: `sites-enabled/` holds a copy rather than a symlink (§5.2), or a
`sed` was run without `-i`. **`sed 's/old/new/g' file` prints to stdout and
changes nothing** — the corrected config scrolls past and looks like success. Use
`sed -i`, then `grep` the file to confirm.

**`[emerg] cannot load certificate ".../fullchain.pem": … No such file or
directory`.** A rename touched the `ssl_certificate` paths as well as
`server_name`, pointing them at a cert lineage that was never issued. nginx will
not start at all. Recover by resetting the vhost to the plain `:80` block in §5.2
and letting Certbot write the TLS config itself:

```bash
sudo cp /etc/nginx/sites-available/postaryx-app.conf /root/postaryx-app.conf.bak
# …re-run the `tee` block from §5.2 verbatim…
sudo nginx -t && sudo systemctl restart nginx     # restart, not reload — there is no live process to signal
sudo certbot --nginx -d app.postaryx.com --redirect --agree-tos -m <your-email>
```

This is why §5.2 writes the file with `tee` instead of editing it: resetting to a
known-good state is one command, and Certbot owns every TLS line in the file.

## 6. Point the app at the domain

One variable, on the VM, in the `.env` next to `docker-compose.yaml` — **not**
`.env.prod`. Compose only reads `.env` for `${...}` substitution.

```bash
cd /opt/postaryx/postaryx-app
echo 'POSTARYX_PUBLIC_URL=https://app.postaryx.com' >> .env
docker compose -p postaryx up -d postaryx
```

No trailing slash. `NEXT_PUBLIC_BACKEND_URL` is built as
`${POSTARYX_PUBLIC_URL}/api`, and a trailing slash there yields `//api`, which
404s on every request. If the file already has a `POSTARYX_PUBLIC_URL` line from
an earlier run, **edit it rather than appending** — Compose takes the last
occurrence, which makes a duplicate work by accident and confuse you later.

**No rebuild is needed, and that is by design.** Postaryx reads `NEXT_PUBLIC_*`
in *server* components and threads them to the client through
`VariableContextComponent` (`apps/frontend/src/app/(app)/layout.tsx`), so they
are runtime values rather than values baked into the JS bundle. This is what
makes the CI-built GHCR image domain-agnostic. See the "SAFE TO CI-BUILD?"
note in `.github/workflows/build-containers.yml`.

Confirm the container actually took the value:

```bash
docker compose -p postaryx exec postaryx env | grep -E 'MAIN_URL|FRONTEND_URL|BACKEND_URL'
# MAIN_URL=https://app.postaryx.com
# FRONTEND_URL=https://app.postaryx.com
# NEXT_PUBLIC_BACKEND_URL=https://app.postaryx.com/api
# BACKEND_INTERNAL_URL=http://localhost:3000
```

Two things to know about `.env.prod` while you're here:

- `NOT_SECURED` must stay **unset**. It disables the secure-cookie requirement
  and is dev-only; set on a real domain it silently downgrades auth.
- `DISABLE_REGISTRATION` set in `.env.prod` **has no effect** — the compose
  `environment:` block hardcodes it to `'false'`, and `environment:` beats
  `env_file:`. Change it in `docker-compose.yaml`, or not at all. Same is true of
  `STORAGE_PROVIDER`, `DATABASE_URL`, `REDIS_URL`, and `TEMPORAL_ADDRESS`. Full
  list in [5. PROD-DEPLOY-PREREQUISITE.md](./5.%20PROD-DEPLOY-PREREQUISITE.md).

## 7. The landing page on Vercel

### 7.1 The project

`clientside-landing` is its own Vercel project — a separate Next.js app from
`postaryx-app`, with its own `pnpm-lock.yaml`. If the two live in one Git
repository, set the project's **Root Directory** to `clientside-landing`. Vercel
auto-detects Next.js and pnpm; no build-command override is needed
(`postinstall` runs `fumadocs-mdx`, which generates the `/docs` sources).

### 7.2 Environment variables

Set these in **Production** *and* **Preview** (Settings → Environment Variables):

| Var | Production | Preview | What breaks without it |
|---|---|---|---|
| `NEXT_PUBLIC_PRODUCT_URL` | `https://app.postaryx.com` | same | **Build/render fails** — `app/page.tsx:26` throws `NEXT_PUBLIC_PRODUCT_URL is required` |
| `NEXT_PUBLIC_SITE_URL` | `https://postaryx.com` | the preview URL, or leave unset | Canonicals, OG tags, sitemap, and JSON-LD all point at the wrong host (§3.1) |
| `NEXT_PUBLIC_INDEXABLE` | `true` | *(leave unset)* | Preview deployments get crawled and duplicate production (§3.2) |
| `DATABASE_URL` | Neon connection string | Neon connection string | The waitlist form 500s on submit (`lib/db.ts`) |

`NEXT_PUBLIC_PRODUCT_URL` takes no trailing slash — `app/page.tsx` appends
`/auth/login`, `/launches`, `/billing`, and `/auth` to it directly. Set it even
before `app.postaryx.com` is live; the build *requires* it, and the links simply
404 until §5 is done.

For `DATABASE_URL`, use the Vercel ↔ Neon integration (Storage → Neon), then run
`clientside-landing/db/schema.sql` once in the Neon SQL editor.

**Env vars added after a deploy are not in the running deployment.** Redeploy
after setting them (Deployments → ⋯ → Redeploy).

### 7.3 Domains and the redirect direction

Vercel → Settings → Domains → add `postaryx.com` and `www.postaryx.com`. Vercel
prints the DNS records to create; take §4's values from this screen.

Then check which way the redirect points, because **Vercel does not reliably
default to the one you want.** §1's table wants:

- `postaryx.com` — the primary, served directly, `200`
- `www.postaryx.com` — redirects to the apex

If it is backwards (apex `308`s to `www`), set `postaryx.com` as the primary
domain, then configure `www.postaryx.com` to redirect to it.

**Set the redirect status code to 308, not 307.** Vercel offers both; 307 is
*Temporary* and tells crawlers to keep indexing `www`, which is the opposite of
what you want. 308 is *Permanent* and consolidates link equity on the apex. It
is a dropdown on the domain's redirect settings, and it is far cheaper to fix now
than after you have been indexed.

This matters more than it looks: `robots.txt` and `sitemap.xml` declare
`https://postaryx.com` as the canonical host (§3.1). If the site actually serves
from `www`, crawlers are told one thing and bounced somewhere else.

### 7.4 The cookie handoff — verify it, don't assume it

`clientside-landing/app/page.tsx` reads `cookies().has("auth")` and flips the nav
between **Login** and **Dashboard**, and the pricing CTA between `/auth` and
`/billing`. That only works if the auth cookie the backend sets on
`app.postaryx.com` is also sent to the apex.

It should be, automatically. `apps/backend/src/api/routes/auth.controller.ts`
sets the JWT with `domain: getCookieUrlFromDomain(process.env.FRONTEND_URL!)`,
and `libraries/helpers/src/subdomain/subdomain.management.ts` reduces that to the
registrable domain via `tldts`:

```ts
export function getCookieUrlFromDomain(domain: string) {
  const url = parse(domain);
  return url.domain! ? '.' + url.domain! : url.hostname!;
}
```

With `FRONTEND_URL=https://app.postaryx.com`, `tldts` returns `postaryx.com`, so
the cookie lands on `.postaryx.com` and both hosts see it. Verified by reading
the source, not by running it. Check it for real:

1. Log in at `https://app.postaryx.com`.
2. DevTools → Application → Cookies. The `auth` row's **Domain** must read
   `.postaryx.com` — with the leading dot — not `app.postaryx.com`.
3. Load `https://postaryx.com` in the same browser. The nav should say
   **Dashboard**.
4. Log out on the app; reload the apex. It should say **Login** again.

Two constraints this depends on. The cookie is a JWT and it is sent to *every*
host under the registrable domain, the marketing site included — the landing only
checks that it exists and never reads the value, and it must stay that way. And
the whole mechanism requires both hosts to share one registrable domain: put the
app on a different domain and this silently stops working, with no error, just a
nav that always says "Login".

> The landing repo's own
> [DOMAIN-AND-INFRA-CHECKLIST.md](../../clientside-landing/ops/DOMAIN-AND-INFRA-CHECKLIST.md)
> §5 says this logic lives in `components/site-frame.tsx`. It doesn't any more —
> `site-frame.tsx` is now deliberately cookie-free (a `cookies()` call would
> force every page in that shell, including `/docs`, to render per-request). Only
> `app/page.tsx` reads the cookie. That checklist also still says 4 OCPU / 24 GB
> is free on OCI; it isn't since June 2026 — see
> [2. ORACLE-CLOUD-SETUP-WALKTHROUGH.md](./2.%20ORACLE-CLOUD-SETUP-WALKTHROUGH.md)
> §0.

## 8. `docker-compose.yaml` review — what to change, and what not to

Read alongside
[4. CONTAINMENT-DEPLOYMENT-PLAN.md](./4.%20CONTAINMENT-DEPLOYMENT-PLAN.md) §3.

**Correct as-is for this topology, leave alone:**

- `ports: ['127.0.0.1:4007:5000']` on `postaryx` — the loopback bind is the
  entire reason the host nginx is the only public listener. Docker's iptables
  rules bypass `ufw`, so a bare `4007:5000` would publish the app to the
  internet regardless of your firewall. Same applies to the `127.0.0.1` prefixes
  on Postgres `5432`, Redis `6379`, Temporal `7233`, and `temporal-ui:8080`.
- The `MAIN_URL` / `FRONTEND_URL` / `NEXT_PUBLIC_BACKEND_URL` block — already
  exactly the three values this topology needs, derived from one variable.
- `BACKEND_INTERNAL_URL: http://localhost:3000` — must stay localhost. This is
  the frontend's *server-side* path to the backend, inside the container. Do not
  "helpfully" point it at the public URL; that adds a network round trip through
  nginx and TLS on every server render.
- `temporal`'s healthcheck plus `condition: service_healthy` on `postaryx` — the
  backend opens its Temporal connection during Nest module init, before
  `app.listen()`. Without the gate you get a container that serves the frontend
  with a dead API, and nginx logging `111: Connection refused` on every `/api/*`.
  Observed twice, per the comment in the file.

**Needs attention:**

1. **`temporal-elasticsearch` is still in the file** (~1.1 GB, the single
   biggest chunk of RAM on a 12 GB box). Temporal's standard visibility on
   `temporal-postgresql` is sufficient for scheduling social posts. Removing it
   means deleting the service block, deleting the `temporal-es-volume`, and
   removing `ENABLE_ES` / `ES_SEEDS` / `ES_VERSION` and the `depends_on` entry
   from the `temporal` service. Same for `temporal-ui` and
   `temporal-admin-tools`, which nothing needs at runtime.

2. **Deleting them on the VM by hand creates a permanent merge conflict.**
   Editing `docker-compose.yaml` in place on the server means every `git pull` on
   the VM conflicts on that file, forever. Two better options, pick one:

   - **`docker-compose.override.yaml` on the VM** (Compose reads it
     automatically, and it's gitignored — nothing to conflict):

     ```yaml
     services:
       temporal-elasticsearch:
         profiles: ['never-start']
       temporal-ui:
         profiles: ['debug']
       temporal-admin-tools:
         profiles: ['debug']
       temporal:
         depends_on: !override
           - temporal-postgresql
         environment:
           ENABLE_ES: 'false'
     ```

     Then `docker compose -p postaryx --profile debug up -d temporal-ui` when you
     actually want the dashboard. Note `depends_on: !override` needs Compose
     v2.24+ (`docker compose version`); on older versions, list-merging appends
     rather than replaces and the ES dependency survives.
   - **Or make the trim the committed default** in `docker-compose.yaml` and take
     the conflict once, in the repo, where you can resolve it deliberately. This
     is the cleaner long-term answer if you're never going to run Elasticsearch.

3. **`DISABLE_REGISTRATION: 'false'`** — flip to `'true'` in the compose
   `environment:` block once your own accounts exist, or randoms who find
   `app.postaryx.com` can sign up and burn your AI/API quota. Setting it in
   `.env.prod` does nothing (§6).

4. **`STORAGE_PROVIDER: 'local'`** with the `postaryx-uploads` volume means
   uploads are served by the container's internal nginx at `/uploads/` and pass
   through your host vhost's `location /`. That works and needs no vhost change.
   It does mean media lives on the VM's 50 GB boot volume and is only as durable
   as your backups — the R2/Cloudflare flip is pre-wired in `.env.prod` and
   documented in
   [4. CONTAINMENT-DEPLOYMENT-PLAN.md](./4.%20CONTAINMENT-DEPLOYMENT-PLAN.md) §7.

5. **`.env` is required and unforgiving.** `POSTARYX_DB_USER`,
   `POSTARYX_DB_PASSWORD`, `POSTARYX_REDIS_PASSWORD`, and
   `POSTARYX_TEMPORAL_DB_PASSWORD` all use `${VAR:?...}`, so Compose refuses to
   start rather than falling back to a weak default. `POSTARYX_PUBLIC_URL` from
   §6 goes in this same file.

## 9. End-to-end verification

Run every one of these. The ones that must *fail* matter as much as the ones
that must succeed.

**From your Mac:**

```bash
# DNS
dig +short postaryx.com                          # Vercel's addresses
dig +short app.postaryx.com                      # <VM_PUBLIC_IP>, one address

# The three public surfaces
curl -sI https://postaryx.com     | head -1      # 200  (landing, Vercel)
curl -sI https://www.postaryx.com | head -1      # 308 → apex (not 307, §7.3)
curl -sI https://app.postaryx.com | head -1      # 200  (app, Oracle)

# Redirect direction — must point at the apex, not away from it
curl -sI https://www.postaryx.com | grep -i '^location'   # https://postaryx.com/

# The API, same origin as the app
curl -s -o /dev/null -w '%{http_code}\n' https://app.postaryx.com/api/
# any HTTP status — 200/401/404 are all fine. 502 or a hang is not.

# TLS is real, not self-signed (no -k anywhere above, on purpose)
curl -sI https://app.postaryx.com > /dev/null && echo "cert OK"

# noindex on the app, allow on the landing
curl -sI https://app.postaryx.com | grep -i x-robots-tag   # noindex, nofollow
curl -sL https://postaryx.com/robots.txt                   # Allow: / — and host/sitemap say postaryx.com
curl -sL https://postaryx.com/sitemap.xml | head -5        # <loc> URLs say postaryx.com

# Nothing internal is exposed. ALL FIVE MUST TIME OUT / refuse.
for p in 4007 5432 6379 7233 8080; do
  if nc -z -G 5 <VM_PUBLIC_IP> "$p" 2>/dev/null; then
    echo "$p: OPEN — THIS IS A PROBLEM"
  else
    echo "$p: closed (correct)"
  fi
done
```

Note the `-L` on the `robots.txt` and `sitemap.xml` checks. Without it, `curl`
prints the body of any redirect it hits — a bare `Redirecting...` — which reads
like a broken file and isn't one.

**On the VM:**

```bash
docker compose -p postaryx ps                        # every container healthy/running
docker compose -p postaryx logs postaryx | grep -i prisma   # migration ran clean
curl -I http://127.0.0.1:4007                        # 200
```

**In a browser — the parts no `curl` can prove:**

- [ ] `https://postaryx.com` renders; nav "Login" links to
      `https://app.postaryx.com/auth/login`; a pricing CTA links to
      `https://app.postaryx.com/auth`.
- [ ] Waitlist form submits successfully (proves `DATABASE_URL` on Vercel).
- [ ] Register an account on `app.postaryx.com`, log in.
- [ ] `auth` cookie's Domain is `.postaryx.com` (§7.4).
- [ ] Reload the apex — nav now says **Dashboard**.
- [ ] Network tab: XHRs go to `https://app.postaryx.com/api/...` and return 2xx.
      No CORS errors. (`Origin not allowed` on the calendar means `FRONTEND_URL`
      doesn't exactly match the browser's URL — scheme, host, no trailing slash.)
- [ ] Upload an image in the composer; it renders from
      `https://app.postaryx.com/uploads/...`.
- [ ] **Schedule a test post a few minutes out and confirm it publishes.** This
      is the only real proof that Temporal and the orchestrator work — a
      frontend that loads proves nothing about them.
- [ ] `sudo reboot` the VM, wait, then re-run the `curl` block above. This is
      what catches non-persisted iptables rules, and it is the single most
      common thing to discover a week late.

## 10. Decommissioning `agentengine.studio`

The rehearsal domain must not stay up. Two live copies of the marketing site is
the duplicate-content problem §3.2 exists to avoid, and `NEXT_PUBLIC_INDEXABLE`
only handles it while crawlers respect `robots.txt`.

### 10.1 On the VM — old certificate and vhost

Do this **after** `app.postaryx.com` has a working certificate, not before.
Deleting a cert that nginx still references puts nginx into the `[emerg] cannot
load certificate` state from §5.6.

```bash
sudo certbot certificates            # list every lineage; confirm app.postaryx.com is there
```

Confirm nothing in the loaded config still points at the old lineage:

```bash
sudo nginx -T 2>/dev/null | grep -i agentengine     # expect no output
```

If that prints anything, fix those files first. Then:

```bash
sudo certbot delete --cert-name app.agentengine.studio
sudo nginx -t && sudo systemctl reload nginx
sudo certbot renew --dry-run                        # renewal still clean afterwards
```

`certbot delete` removes the lineage under `/etc/letsencrypt/`. It does **not**
revoke the certificate. Revocation is only warranted if the private key was
exposed; for a retired hostname, deletion is the right and sufficient action. If
you do need it: `sudo certbot revoke --cert-name <name> --delete-after-revoke`.

Remove any leftover vhost for the old host:

```bash
ls -l /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/postaryx-app-agentengine.conf   # if one exists
sudo nginx -t && sudo systemctl reload nginx
```

### 10.2 On Vercel

Settings → Domains → remove `agentengine.studio` and `www.agentengine.studio`
from the project. Alternatively, keep them attached and set both to **redirect to
`postaryx.com`** — worth it only if the rehearsal domain picked up real inbound
links, which it almost certainly didn't.

Delete the rehearsal Neon database if you provisioned a separate one, so test
signups don't linger in a table you might later mistake for the real waitlist.

### 10.3 DNS and the domain itself

Remove the `app` record pointing at `<VM_PUBLIC_IP>` from the
`agentengine.studio` zone, so a retired hostname cannot resolve to live
infrastructure. Then either let the registration lapse or park it.

### 10.4 Social OAuth callbacks

Each provider needs an exact redirect URI, built as
`${FRONTEND_URL}/integrations/social/<provider>` — e.g.
`https://app.postaryx.com/integrations/social/linkedin` (see
`libraries/nestjs-libraries/src/integrations/social/linkedin.provider.ts`). Any
app registered against the rehearsal host needs its URI updated. Most providers
allow several URIs per app, so add the `postaryx.com` variant alongside the old
one during cutover, then remove the old one here.

### 10.5 Sessions

`tldts` reduces `app.postaryx.com` to `postaryx.com`, so the auth cookie now
lands on `.postaryx.com`. Anyone still holding an `.agentengine.studio` cookie
appears signed out. That is correct behaviour, and worth knowing before someone
reports it as a bug.

### 10.6 Last step

Submit `https://postaryx.com/sitemap.xml` to Google Search Console.

## 11. Appendix — the single-VM alternative

If you'd rather not use Vercel, the landing can run on the same box: build it
into its own small container (or `next start` under pm2), publish it on
`127.0.0.1:3005`, and add a second vhost.

```nginx
server {
    listen 80;
    server_name postaryx.com www.postaryx.com;
    location / {
        proxy_pass http://127.0.0.1:3005;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Upgrade           $http_upgrade;
        proxy_set_header Connection        $connection_upgrade;
    }
}
```

Then `sudo certbot --nginx -d postaryx.com -d www.postaryx.com -d app.postaryx.com --redirect`
for one cert covering all three, and add a `www` → apex 308.

**What it costs you.** Another ~300–500 MB resident and a Next.js build on a box
that
[4. CONTAINMENT-DEPLOYMENT-PLAN.md](./4.%20CONTAINMENT-DEPLOYMENT-PLAN.md) §6
already moved builds *off* for OOM reasons — so the landing would need CI builds
too. Marketing copy changes become server deploys. The Neon waitlist still needs
a `DATABASE_URL`. And the apex — your SEO surface — goes down whenever the VM
does.

**Recommendation: don't.** Vercel is free at this scale, keeps the apex up
independently of the product, and is what the landing repo already assumes. This
appendix exists for the case where you specifically want everything on
infrastructure you control.
